## Server contract

- `billing_subscriptions`: one immutable owner per `(provider, provider_environment, provider_subscription_id)`. Use Stripe's subscription ID or Play's purchase token. `product_id` is the Stripe price ID or Play subscription product ID. Required `status` preserves provider state; `verified_at` records successful server verification. Neither field alone grants access. Updates refresh `updated_at` automatically.
- `provider_environment`: `test` for Stripe sandbox/test events or verified Play test purchases; `live` for live purchases. Determine this from trusted provider data/configuration, never a client flag. Both provider identities and event identities are scoped to this environment.
- Subscription owners may select the explicitly granted safe columns. They cannot insert, update, delete, or select purchase tokens/customer identifiers. Client `select('*')` on this table intentionally fails. Service-role credentials remain server-only.
- For Play replacements, verify the provider's linked purchase and bind the replacement token to the established owner before storing it. Do not accept a client-supplied owner or transfer an existing purchase to another account.
- `billing_events`: a server-only ledger keyed by provider, environment and provider event ID. Store Stripe `event.id` or authenticated Pub/Sub `messageId`. Leave `subscription_id` null until a verified subscription is identified. Cross-check the subscription's provider/environment when linking it. Store only a short error code; no raw webhook body, email or token.
- Mark `processed` or `ignored` with a non-null `processed_at` in the same statement. Other states require a null `processed_at`. Use `attempt_count`/`last_attempt_at` for retries; the schema does not claim events or schedule workers.
- Normal profile edits and owner deletion remain available. Stripe customer ID, subscription status, period end and Elo are no longer client-writable. Existing server-role writes and the judge's SECURITY DEFINER function retain their access.

The permission model uses both row ownership and column privileges; see [PostgreSQL's GRANT documentation](https://www.postgresql.org/docs/17/sql-grant.html).
